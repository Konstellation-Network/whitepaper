\section{Account abstraction}
\label{sec:aa}

Konstellation is intended to be a chain on which smart-account wallets,
passkey-based accounts and sponsored transactions work on day one, without
waiting for third parties to deploy infrastructure contracts. Almost all of
that is application-layer work; the chain's contribution is to preinstall the
canonical contracts at genesis and to expose the two protocol-level pieces
those wallets need (ENGINEERING \S14).

\subsection{ERC-4337: EntryPoints preinstalled}

The ERC-4337 \code{EntryPoint} contracts, versions 0.7 and 0.8, are part of
the genesis state at their \textbf{canonical mainnet addresses} --- the
addresses wallet SDKs and bundlers hard-code --- together with the
\code{SenderCreator} each one depends on, a \code{CREATE2} deployer, and the
preinstalls \code{cosmos/evm} ships by default (Table~\ref{tab:preinstalls}).

A preinstall never runs its constructor. Each \code{EntryPoint} would, when
deployed normally, create its \code{SenderCreator} and store the address as an
immutable; because that address cannot be recreated after genesis, both
\code{SenderCreator}s are preinstalled too and the node refuses to initialise
if an \code{EntryPoint} is present without its pair. Without them every user
operation carrying \code{initCode} would revert.

\subsection{Passkeys: the p256 precompile}

Passkey and WebAuthn accounts sign with the NIST P-256 curve. Verifying such a
signature in Solidity is prohibitively expensive without native support.
\code{cosmos/evm} ships the RIP-7212 / EIP-7212 \code{p256} precompile at
\code{0x0000000000000000000000000000000000000100}; Konstellation exposes it
unchanged, so passkey-based smart accounts work at the cost of a precompile
call. This address is one reason the Osaka fork is not enabled
(\dref{D17}): Osaka's native EIP-7951 P-256 precompile lands at the same
address, and which one wins is undefined upstream.

\subsection{EIP-7702}

EIP-7702 lets an externally owned account delegate its code to a contract by
signing an authorisation, so an existing key can behave as a smart account
without migrating funds. It requires the Prague fork rules in the EVM
configuration. Konstellation runs the \textbf{Prague} (Pectra) fork from
genesis, which is what the pinned \code{cosmos/evm} release activates by
default; the later Osaka (Fusaka) fork is deliberately not enabled, because
upstream never activates it and its own code only branches on Prague, so it is
an untested path, and because of the precompile-address collision above
(\dref{D17}, decided 2026-09-21). Contracts are compiled for the
\code{prague} EVM version. The chain's integration tests
exercise 7702 delegations end to end, including the interaction with the
compliance module (\S\ref{sec:compliance}):

\begin{itemize}
\item The authority of every 7702 authorisation in a transaction is treated as
  a signer for compliance purposes, so a relayer cannot install code on a
  frozen account.
\item A freeze clears an existing delegation on the frozen account; lifting the
  freeze and re-delegating restores the wallet with its storage intact.
\end{itemize}

\subsection{Machine payments (x402)}

x402 is an HTTP payment standard, not a blockchain protocol; it needs a
stablecoin implementing EIP-3009 (\code{transferWithAuthorization}), a
facilitator that knows the chain, reliable public RPC and fast finality, which
CometBFT provides. None of it requires chain changes. \todo{Whether an
EIP-3009 stablecoin will exist on Konstellation at or near launch, and who
would issue it, is not decided; x402 support is an intent, not a commitment.}
